## 제품의 핵심 입력은 문제가 아니라 풀이 로직이다

새로운 모의고사·수능 유형이 나오면 **문제, 정답, 해설에서 재사용할 풀이 로직을 먼저 확정**한다. 아무 문제나 넣어 비슷한 문장을 만드는 제품이 아니다. `풀이 로직 카드`의 단계 수는 문제마다 다르다. 원본 풀이에 번호나 소제목이 있으면 그대로 보존하고, 없으면 실제 판단 또는 계산 방법이 바뀌는 지점만 나눈다. 화학 샘플의 3단계는 그 문제의 풀이 예시이며 모든 문제의 공통 형식이 아니다.

AI는 대상·상황·수치를 바꾸되 새 문제도 기준 풀이의 처음부터 마지막 단계까지 같은 순서로 모두 사용해야 풀리도록 만든다. 어느 단계를 문제 조건으로 미리 주거나 다른 풀이법으로 바꾸면 변형 성공으로 보지 않는다. 화면은 1~12개의 단계를 동적으로 보여 주며 결과도 같은 개수로 1:1 대조한다.

첫 기준선의 생성 결과는 **기준 풀이 전체를 사용하는 쌍둥이 문제 1개**다. 화면에는 `문제 이미지`와 `풀이 이미지` 칸을 항상 따로 표시한다. 한 장에 문제와 풀이가 함께 있으면 같은 파일을 두 칸에 넣어 역할을 명확히 지정한다. 풀이가 없으면 문제 이미지만 읽고 `STEP별 풀이 생성`을 실행한다. AI가 원문 문제를 먼저 풀고 실제 풀이에 필요한 만큼 단계화한 뒤, 그 문제와 풀이 카드로 쌍둥이 문제를 만든다.

전체 쌍둥이는 단계별 문제를 만드는 기준선이다. 다음 MVP에서는 같은 로직 카드로 **앞에서부터 한 단계씩 추가되는 누적 문제**를 만든다. STEP 수는 문제마다 다르며 3단계로 고정하지 않는다.

## 다음 핵심 MVP: STEP별 연습 문제 세트

단계별 문제는 STEP 하나씩을 따로 떼어내는 방식이 아니다. 학생이 앞 단계부터 직접 연결하도록 `STEP 1`, `STEP 1+2`, …, `STEP 1~N` 순서로 필요한 로직을 하나씩 늘린다. N은 입력 문제의 실제 풀이를 분석해서 정하며 특정 과목이나 고정 숫자를 사용하지 않는다.

| 생성 순서 | 학생이 직접 해야 하는 로직 | 문제의 목표 |
|---|---|---|
| 1단계 문제 | STEP 1 | 첫 번째 핵심 판단·계산까지만 묻기 |
| 2단계 문제 | STEP 1+2 | 첫 판단부터 두 번째 중간 결과까지 묻기 |
| 중간 단계 문제 | STEP 1~k | k번째 중간 결과까지 묻기 |
| 전체 쌍둥이 | STEP 1~N | 원본의 모든 로직으로 최종 답까지 구하기 |

원본 풀이가 N단계면 결과도 정확히 **N문제**다. 2단계 풀이면 2문제, 3단계 풀이면 3문제, 5단계 풀이면 5문제를 만든다. 앞 단계를 건너뛴 `STEP 2만`, `STEP 2+3만` 문제는 첫 MVP에서 만들지 않는다.

STEP 수를 정할 때 문장 수나 계산 줄 수를 세지 않는다. 다음 단계의 입력으로 재사용되는 **의미 있는 중간 결론**이 생기는 지점에서만 나눈다.

- 풀이가 제공되면 원본 풀이의 번호·소제목·논리 전환을 우선 보존한다.
- 번호가 없으면 판단 방법이 바뀌거나 중간 결과가 다음 계산의 입력이 되는 지점에서 나눈다.
- 단순한 식 정리와 같은 계산을 여러 STEP으로 부풀리지 않는다.
- 풀이가 없으면 원본 문제를 먼저 끝까지 풀고 검산한 다음 실제 풀이 흐름을 STEP으로 만든다.

각 풀이 로직 카드는 한 문장만 저장하지 않고 다음 구조를 가진다.

```text
STEP 번호 / 이 단계의 목표 / 필요한 입력 / 수행할 판단·계산 / 중간 출력 / 선행 STEP
```

예를 들어 현재 반응량 샘플은 다음처럼 나눈다.

| 생성 문제 | 반드시 사용하는 로직 | 이 문제에서 묻는 것 |
|---|---|---|
| STEP 1 문제 | 가정과 모순으로 한계 반응물 결정 | 각 실험의 한계 반응물과 근거 |
| STEP 1+2 문제 | 한계 반응물 결정 → 반응 후 질량·몰수 정리 | 반응 후 남은 물질과 생성량 또는 완성된 반응 후 표 |
| 전체 쌍둥이 | 한계 반응물 결정 → 반응 후 정리 → 상대 몰비·몰질량 계산 | 최종 몰질량 비 또는 선택지 |

### 화면의 최소 흐름

1. 문제·풀이 이미지에서 실제 STEP 카드를 추출한다.
2. 교사가 단계 설명과 선행 STEP을 확인한다.
3. 버튼을 `단계별 N문제 만들기`로 표시하며 N에는 현재 확인된 실제 STEP 수를 넣는다.
4. 결과를 `STEP 1 → STEP 1+2 → … → STEP 1~N 전체 쌍둥이` 순서로 보여 준다.
5. 각 결과에는 `이 문제를 풀 때 필요한 STEP`을 표시한다.

### 생성·검사 하네스

- 각 문제는 STEP 1부터 지정된 마지막 STEP까지 모두 같은 순서로 사용해야 한다.
- STEP 1+2 문제에 STEP 1의 결론을 미리 주면 STEP 1 연습이 사라지므로 실패다.
- 지정된 마지막 STEP보다 뒤의 로직을 알아야 풀 수 있으면 단계 문제로 실패다.
- 쉬운 문제라도 단순 암기형으로 바꾸지 않고 해당 STEP의 실제 판단·계산을 수행하게 한다.
- 전체 쌍둥이는 어떤 중간 결론도 미리 주지 않고 모든 STEP을 사용해야 한다.
- 모든 문제는 독립 검산, 정답 하나, 보기·해설 일치, 문장·표·그림 검사를 각각 통과해야 한다.

여기서 “학습시킨다”는 말은 MVP에서 모델 가중치를 문제마다 다시 학습한다는 뜻이 아니다. 확인한 풀이 로직 카드를 현재 요청의 문맥으로 보내고, 생성·검산·평가에 같은 카드 ID와 버전을 사용하는 방식이다. 교사가 승인한 카드와 좋은 변형을 쌓아 RAG로 재사용하고, 충분한 승인 데이터와 고정 평가셋이 생긴 뒤에만 파인튜닝을 검토한다.

웹 v24에서는 기준·생성·결과 그림을 클릭하면 확대 창이 열린다. 확대·축소·화면 맞춤, 스크롤, 닫기·Esc와 원래 이미지로 초점 복귀를 지원한다. 웹 v28에서는 풀이 로직을 고정 3단계에서 실제 단계 수로 바꾸고 화면·생성 요청·검토 하네스에 연결했다.

## 2026-09-19: 원래 요구사항으로 돌아간 첫 MVP

요구사항 원본은 `docs/샘플/프로그램.pdf` 1~3페이지다. 핵심은 문제를 푸는 로직을 유지하는 응용 문제와 해설이며, 숫자만 바꾼 다른 유형이 아니다. 첫 입력은 `02페이지_킬러문제와해설.jpeg`처럼 문제·정답·해설이 함께 있는 한 장이다.

1. 문제 이미지는 필수, 풀이 이미지는 선택으로 넣는다. 한 장에 둘 다 있으면 같은 파일을 두 칸에 넣는다. 선택한 모델(Gemma 로컬 / DeepSeek API)이 문제 본문과, 풀이가 있을 때 기준 정답·해설·실제 풀이 단계를 역할별로 분리한다.
2. 풀이 이미지가 없으면 `STEP별 풀이 생성`을 누른다. 지원 반응량 유형은 코드 계산기로, 나머지는 선택 모델로 원문 문제를 먼저 풀어 정답·해설·필요한 풀이 단계를 만든다. 원본 미리보기와 자동 입력 결과를 확인하며 판독불가·몰질량 OCR 혼동·원본 정답 불일치는 쌍둥이 생성 전에 중단한다.
3. 응용 문제 하나를 생성한다. 반응량 템플릿은 질량을 2~5배로 바꾸고 상댓값을 유지하며, 남은 기체 종류를 직접 추론하게 한다. 가능한 A/B 조합의 공통 소비 질량비를 계산하여 유일성을 검증하고, 가정→모순→한계 반응물 판단의 풀이를 포함한다.
4. 별도 문항 검토에는 기준 풀이도 전달해 같은 논리가 필요한지 확인한다. 기존 PNG 렌더링·이미지 검사·오류 출력 차단을 유지한다. 결과의 원본 확인란에서 기준 정답·풀이도 볼 수 있다.

첫 MVP의 응용은 같은 무차원 정답을 유지하는 쌍둥이 문항이다. 단계별 쉬운 문항, 반응계수 자체를 바꾸는 역설계, OMR·맞춤 주간지는 다음 단계다. 모든 과목의 계산을 코드로 검산한다고 보장하지 않는다. 문제+풀이 읽기도 선택한 모델을 사용한다. DeepSeek 또는 둘 다를 선택하면 읽기 시 원본 이미지를 DeepSeek API에 전달하며 읽기·생성·검토의 비용이 각각 발생한다. Gemma는 로컬 처리한다.

### 이번 원본 샘플의 실제 검증

- 원본 JPEG를 손으로 재작성하지 않고 선명하게 정규화한다. 넓은 흰 여백이 확인되면 좌우 열로 나누고, 명확한 파란 문제 테두리까지 확인되면 문제·왼쪽 풀이·오른쪽 풀이 3영역에 역할을 표시한다. 영역의 픽셀은 정규화 원본과 동일하며 전체 내용을 보존한다. 구분 근거가 없으면 경계를 추측해 자르지 않는다.
- DeepSeek로 문제·답·풀이를 분리하고 실제 생성 요청을 실행했다. 원본 검산은 b=3, x=15, 답 2/5다. 생성 예시는 전체 질량 5배, 남은 기체 종류를 추론하는 표, 정답 ⑤ 2/5다. 수치·해설은 코드 템플릿으로 재구성하므로 AI 단독 작성이라고 표시하지 않는다.
- 원본 STEP 1 가정·모순·한계 반응물, STEP 2 반응 후 질량·몰수, STEP 3 상대 몰비·몰질량을 유지했다. 별도 DeepSeek 문항 검토 4항목과 로컬 Qwen 최종 PNG 대조가 통과했다. 자동 검사가 교사 승인을 대신하지 않는다.
- Gemma의 초기 원본 읽기는 몰질량 용어와 해설 수치를 잘못 판독했다. 정규화·열 분할을 연결했지만 같은 원본의 Gemma 전체 성공은 검증하지 않았다. 이번 MVP 확인에는 DeepSeek를 선택한다.
- 실제 연결 테스트에서 풀이 표를 본문에 섞고 몰질량을 물질량으로 읽은 사례는 생성 전에 차단했다. 문제·풀이 영역 표시와 작은 문제 영역을 별도로 읽는 처리를 보완했다. 재검사에서는 실제 로컬 웹 업로드→DeepSeek 읽기→원본 이미지 포함 생성→텍스트 검사→브라우저 PNG 출력→웹 이미지 검사까지 통과했다. 최종 웹 예시는 질량 3배, 정답 ⑤ 2/5다. 원본 전사의 필기는 확인 대상이며 새 문제 표에서는 x의 계산값과 잔류 물질 종류를 제외한다.
- 웹 v28 기준 Core 188/188, 웹·렌더링 47/47 통과. 실제 문제/풀이 분리 입력에서 판독 모델이 원본 풀이를 4단계로 나눴고, 생성 결과도 같은 4단계와 순서를 유지했다. 코드 검산·문장·조건·수치·그림 필요 여부와 최종 PNG 대조를 포함한 하네스 전 항목이 통과했다. 증거: `artifacts/evidence/web/material-web-separate-smoke.json`, `material-web-separate-output.png`. 기존 v27에서는 문제만 입력, 문제/풀이 분리, 동일 이미지 두 칸 입력의 세 경로도 통과했다. 외부 HTML·JS는 로컬 최신 파일과 일치하고 익명 API에는 401 인증이 유지된다.

### 개발 테스트 도구 실행

`MaterialMvpSmoke.exe`는 일반 프로그램이 아닌 개발 테스트 도구다. 프로젝트의 `MVP 테스트 실행.cmd`가 최신 Windows 타깃을 빌드하고 저장된 판독 결과의 코드 검산을 실행한다. 기본 실행은 AI를 호출하지 않는다. 일반 화면은 `프로그램 실행.cmd` 또는 웹에서 이용한다.

구형 `bin/Debug/net10.0`, `bin/Release/net10.0` 결과는 `artifacts/retired-material-smoke-*`로 백업했다. 새 빌드 위치는 `net10.0-windows10.0.19041.0`이다. 실행 폴더와 관계없이 프로젝트 경로를 찾으며, 인자 없는 직접 실행은 사용법만 표시한다. 실패는 종료 코드 1과 `artifacts/evidence/web/material-mvp-smoke-error.log`로 기록한다. `--deepseek-reader`, `--generate`, `--text-review-only`는 외부 API 비용이 발생한다.

## 09/17 인식·생성 오류 수정

기존 저해상도 캡처의 Windows OCR은 본문이 깨졌고, 생성은 긴 답변이 잘리는 오류가 있었습니다. 로컬 이미지 인식 서버를 연결하고 길이·추론 설정과 보기 배열 한도를 맞췄습니다. 반응량 표를 별도로 재조판한 이미지에서 3개 실험의 질량을 함께 2배로 변형하는 경로를 검증했습니다. 이 재조판 자료는 원본과 배치·수식 표현·필기가 다릅니다. 현재 웹 기본 예시는 PDF에서 추출한 반응량·분자 구조 원본으로 교체했고, 제작 자료는 접힌 테스트 영역으로 분리했습니다. 원본에서 같은 수준의 인식·생성 품질을 확인하는 작업은 남아 있습니다. 인식한 본문을 사용자가 확인·수정한 뒤 생성합니다.

반응량 표의 한 유형은 `ReactionMassCheck`로 질량 소비비·상대 몰분율·b·x·정답을 계산합니다. 표가 모순되거나 계수가 양의 정수가 아니거나 검산 답이 보기에 없으면 실패로 안내합니다. 결과 해설과 정답 번호는 이 계산에 연결합니다. 자동 테스트 57/57, 외부 실제 이미지→변형 생성 검사 14/14 통과. 증거는 `artifacts/evidence/web/verified-image-import.json`, `verified-image-generation.json`, `web-smoke.json`입니다.

저해상도 원본의 ‘몰질량/물질량’ 오독은 남았습니다. 원본과 인식 본문을 비교·수정해야 하며, 분자 구조 그림 등 다른 유형의 인식·정답 품질은 이 예시 통과만으로 완료 판정하지 않습니다.

## Gemma 원본 이미지 직접 입력 (0.5.0)

이미지 문제는 전용 Gemma 서버 8092의 vision=true를 확인한 뒤 원본 image_url을 본문과 함께 보낸다. Qwen은 본문 전사·시각 관계 분석·생성 후 대조를 유지한다. 이미지 지원이 꺼진 서버의 자동 텍스트 대체는 금지했다. 67개 Core 테스트와 별도 재조판 이미지로 외부 이미지→생성 검사 17개를 통과했다. 재조판 표 문제는 실제 Gemma 이미지 생성 후 코드 검산으로 정답 2/5를 확인했다. Gemma가 OCR 본문 없이 별도 제작 그래프 좌표를 읽는 시험도 통과했다. 이 결과는 PDF 원본 표·분자 구조 문제의 전체 인식·생성 검증을 뜻하지 않는다.

기존 공유 8089 서버를 유지하기 위해 CPU/GPU를 함께 쓰며, 표 문항의 Gemma 생성은 약 173초 걸렸다. 진행 표시·취소와 300초 제한을 유지한다. Windows 설치판은 0.5.0으로 반영했고 Core DLL이 웹과 같은지, 기존 workspace.json 해시가 그대로인지 확인했다. Windows 실제 GUI 및 그림 포함 PDF 출력 검증을 대신한 것으로 보지 않는다.

외부 실제 브라우저에서도 Gemma 원본 이미지 1장 직접 입력 표시, x=3→5 질문, 정답 10, 기준 그림 1700×1545 정상 로드를 확인했다. Gemma 생성은 약 81초였다. 증거는 `gemma-graph-smoke.json`이다. 출력 본문에 OCR 축 눈금과 불필요한 주석 목록이 남는 문제는 별도 개선이 필요하며, 그림 자체를 다시 그린 결과는 아니다.

## 이미지 입력 장애와 풀이 입력 모드 (0.6.0)

Gemma/Gemini 웹 비교: 같은 기준 자료와 원본 렌더링 이미지를 두 모델에 각각 직접 전달한다. Gemini는 공식 generateContent API의 inlineData와 JSON 응답 형식을 사용하고 입력 식별값·보기·완료 여부를 검증한다. 지원하는 반응량 유형은 같은 코드 계산·본문·정답 검산을 적용하며, 그 밖의 Gemini 그림 결과는 교사 확인이 필요한 AI 초안이다. Gemma의 Qwen 시각 재대조와 Gemini의 직접 이미지 입력을 동일한 검증 수준으로 주장하지 않는다. API 키는 서버 비공개 런타임에만 저장하며 정적 배포 제외·외부 요청 404를 확인했다. 모델별 완료/실패를 분리하여 부분 성공을 유지한다. 일시 서버 오류(500/502/503/504)는 두 번만 재시도하고 인증/할당량 오류는 자동 재시도하지 않는다. 79개 Core 테스트 통과. Google 모델 목록은 3.8을 포함했으나 실제 문항 요청은 높은 수요로 503을 반환했고, 동일 응답 스키마의 2.5 Flash는 정상 생성했다. 기본값은 2.5이며 3.8은 명시적으로 선택할 수 있다. Windows UI의 Gemini 비교 기능은 이번 웹 작업 범위에 포함하지 않았다.

실제 검증: 외부 브라우저의 ‘둘 다 비교’에서 탄산칼슘 10 g 텍스트를 두 모델이 각각 20 g 문제로 변형하여 정답 ② 0.2 mol과 다른 해설을 표시했다. Gemma 2,429 토큰, Gemini 2.5 Flash 3,886 토큰. Gemini 상세 결과 선택·비교 결과 유지·복사/PDF 버튼 활성화를 확인했다. 최초 3.8 실패 시 Gemma 성공 결과가 남는 것도 확인했다. 기록: `artifacts/evidence/web/comparison-browser-check.json`.

원본 이미지 Gemini 검사에서는 긴 표 본문을 enum으로 강제했을 때 출력 한도(MAX_TOKENS) 오류를 재현했다. ### 웹 통신 끊김과 작업 복구 (v9)

사용자가 보낸 상세 오류는 `Failed to fetch`였다. 조사 시 외부 게이트웨이와 Windows 역방향 터널은 정상 연결돼 있었다. 해당 사용자의 순간적인 연결 끊김 원인까지 확정한 것은 아니다. 기존 프론트는 첫 fetch 오류로 상태 조회를 중단하고 생성 작업 번호를 지웠다.

API 기준 경로를 실행된 app.js의 폴더로 고정해 접속 주소의 끝 슬래시에 의존하지 않는다. GET은 요청당 8초 한도와 최대 4회 재시도를 적용하고, 응답 본문 수신 중 끊김·502/503/504도 같은 복구 대상으로 다룬다. 생성 POST에는 요청 번호를 부여하고 서버에서 입력·모델·원본 식별값을 검증해 같은 요청이면 기존 작업 번호를 돌려준다. 동시 요청도 한 번만 시작한다. 내부에서 새로 만들어지는 draft Id는 중복 판별에서 제외한다. 파일 업로드 POST는 자동으로 재전송하지 않는다.

미완료 작업 또는 전달 여부가 불명확한 생성 요청을 sessionStorage에 보관한다. 조회 재시도가 소진돼도 `진행 중이던 생성 결과 다시 확인`으로 기존 작업을 복구한다. 원본·본문을 유지하고 연결 실패를 모델 생성 실패와 다른 제목으로 표시한다. 서버 재시작으로 작업 자체가 사라졌다면 그 사실을 안내한다. 서버의 모델 실패는 모델·단계·작업 번호를 로그에 남긴다. 인증은 유지한다.

Core/웹 작업 등록 테스트 115개, JavaScript 테스트 15개 통과. 별도의 localhost 테스트 서버에서 실제 브라우저 연결을 다섯 번 강제로 끊고 복구해 기존 DeepSeek 결과와 PNG가 표시됨을 확인했다. 이 브라우저 검사 중 새 생성 POST는 0회였다. 공개 v9 파일이 소스와 동일하며, 인증 없는 외부 API 요청 12회는 모두 정상 401로 반환돼 전송과 인증 경계를 확인했다. 증거는 `artifacts/evidence/network-recovery/`에 보관했다. 이 검사는 사용자의 외부 브라우저에서 새 DeepSeek 생성을 끝까지 재실행한 검사가 아니다.

### 표·보기·수식·해설 표시 정리 (v17)

사용자 화면과 일치하는 기존 완료 결과 0dc960bee63e4d1d930cbfb7ec3fd6e6에서 본문 Markdown 보기 표와 choices가 중복되는 것을 확인했다. 두 열 값이 순서와 내용까지 5개 보기와 모두 일치할 때만 보기 표를 본문에서 분리하고, 열 제목을 보존한 한 개 표로 표시한다. 값이 다른 표나 ㄱ·ㄴ·ㄷ 진술은 지우지 않는다. 독립 데이터 표도 각각 표시하며 표 셀은 HTML로 해석하지 않는다.
