## 1. 사용자가 만들려는 제품

핵심은 아무 이미지에서 문제를 무작위로 만들어내는 프로그램이 아니다. **교사가 제공한 문제와 풀이 방법을 이해하고, 그 풀이 로직으로 풀리는 단계별 연습 문제와 쌍둥이 문제를 만드는 시스템**이다.

1. 문제 이미지는 필수, 해설 이미지는 선택이다.
2. 한 이미지에 문제와 해설이 모두 있으면 문제 입력과 해설 입력에 같은 파일을 넣을 수 있어야 한다.
3. 해설을 주면 원본의 보조 문자, 치환, 가정, 실험 비교, 모순 판정, 풀이 순서를 보존한다. AI가 임의의 다른 방법으로 교체하면 안 된다.
4. 해설이 없으면 먼저 풀이를 만들고 실제 로직 단위로 STEP을 정리한다.
5. STEP 수는 원본 풀이에 따라 달라진다. 모든 문제를 강제로 3 STEP으로 만들거나 사소한 계산을 쪼개 6~11 STEP으로 늘리면 안 된다.
6. STEP 1만 이해하면 풀리는 연습, STEP 1~2가 필요해야 풀리는 누적 연습, 전체 로직이 필요한 최종 쌍둥이 문제를 만든다. 3 STEP 원본에서는 보통 3문항 한 세트다.
7. 단순 수치 변형과 그 이상의 통합 변형을 관리자가 선택할 수 있어야 한다.
8. 통합 변형은 숫자만 바꾸거나 불필요한 조건을 늘리는 것이 아니라 앞의 문제 아이디어와 풀이 관계를 실제로 통합해야 한다.
9. 사람의 문제별·해설별 피드백과 전체 생성 지침을 저장하고, 승인된 내용을 다음 생성에 적용한다. 교사의 선호를 쌓아가는 것이 목적이다.
10. 조건·수치·답·해설·그림·표현·PDF를 검사하되 검사기가 없는 유형을 영원히 막거나, 검토 모델 오판 때문에 비싼 전체 재생성을 반복하지 않아야 한다.

## 5. 현재 일반 생성 흐름과 고장 지점

1. 인증 후 자료를 넣는다. 분리 모드에서는 questionFile/solutionFile 역할을 구분한다.
2. `/api/import`가 이미지 원본/읽기용 view를 만들고 DeepSeek 또는 Gemma에 보낸다.
3. 문제 본문과 해설/STEP이 분리되어 반환된다. 원본은 sourceId로 보관한다.
4. 문제만 넣었다면 `/api/solution`으로 해설/STEP을 먼저 만든다.
5. 분석 결과 확인 후 `/api/generate`를 호출한다. 사용자에게 보이는 확인 체크가 AI 정확성을 증명하는 것은 아니다.
6. 원본 문제의 지원 독립 계산기로 답을 비교하고 원본 풀이 방법/변형 정책/STEP 범위를 확인한다.
7. 전체 지침 + 승인 피드백 검색 결과를 `learningContext`로 만든다.
8. `LearningStagePlan`에서 단계별 초안을 만든다. 코드 지원 유형은 수치/문항 템플릿이 있고, 그 외는 LLM 생성 및 검토/보완 경로다.
9. `prepared` 상태는 내부 검토 통과 초안이다. 전체 세트가 통과해야 `ready`로 공개한다. 실패 단계만 재사용·재검토하려는 구조다.
10. 완료 결과를 내부 staged 학습 기록에 보관할 수 있지만 사용자 목록에는 명시적으로 “학습 데이터 추가”한 세트만 나타나야 한다.
11. PDF/학습 저장은 결과 보고서 렌더러를 거쳐 미리 PDF를 만든 뒤 연결한다.

고장 원인은 한 가지가 아니다: 원본 OCR 누락/필기 혼입, 모델 JSON/출력 한도, LLM의 조건·수치 변경, AI 검토자의 잘못된 수학 지적, 독립 계산기 미지원, 체크 순서/상태 혼동, 서버/터널 연결, 렌더링/PDF 중복 등이 겹쳤다. “선명한 이미지를 넣으라” 또는 “다시 테스트해 달라”만 반복해서는 해결되지 않는다.

## 6. 사용자 불만/실패 사례 — 숨기지 말 것

### 교사 피드백의 원뜻

- 원본 해설을 잘못 읽고 AI가 자기 방법으로 풀었다. 그 방법이 원본보다 조잡했다.
- 쌍둥이 문제에 관련 없는 조건·불필요한 서술이 들어갔다.
- STEP 1 또는 STEP 1~2 연습은 괜찮아도 전체 문제는 단순 숫자 변경에 머물렀다.
- 앞 연습 문제 아이디어를 통합하는 최종 문제와 단순 숫자 변형을 선택할 수 있어야 한다.
- 보조 문자를 도입해 풀이가 간단해지는 교사의 방법을 계속 써먹어야 한다.
- 저장 피드백이 실제 다음 생성에 영향을 주어야 한다. “학습했다”는 라벨만 있으면 안 된다.

### 심각했던 정확성 문제

- 산염기 입력 해설이 틀린 정답 ④를 주장하고 계산이 안 맞자 “보기 오류”라고 합리화했다. 올바른 계산은 ② 3/4이었다.
- 음이온/양이온 비 >1을 산성으로 해석해 전하 균형과 모순되었다.

### 8.1 `src/EduMaster.Core/ReactionLearningPlan.cs`

- 현재 version: `reaction-learning-plan-v3-compiled-feedback`.
- `Create(ProblemDraft draft, int number, int total, string explanationStyle="teacher")`.
- 지원 조건은 원본과 같은 **A+bB→2C+2D 몰질량/반응량 + 교사 3 STEP n,m 풀이**에 한정된다. 매칭 실패 시 일반 LLM 경로다.

## 14. RAG/학습 구현의 실제 범위

`src/EduMaster.Web/LearningArchive.cs`:

- 파일 기반 JSON 아카이브, 원본 이미지/완료 결과/문제별 피드백/승인 정보/pdfReportId.
- pending→approved/rejected 명시적 검토. 등록한다고 자동 승인되는 것은 아니다.
- `AddedManually=true`인 학습 자료만 목록/검색 대상으로 삼는다. internal staged 결과와 구분한다.
- `Retrieve(draft,maxExamples=3)`는 단어 집합의 겹침 비율을 사용한다. score threshold 0.18, 사례 수 1~5 제한.
- 분모는 `min(단어집합크기)`인 overlap coefficient다. 임베딩/cosine/vector DB가 아니다.
- 승인된 method 피드백 최근 3개를 교사 선호로 먼저 첨부하고, 유사 문제의 approved feedback을 최대 3개씩 첨부한다.
- 최종 검색 prompt context 4,000자 제한. 길면 잘려 일부 지침이 빠질 수 있다.
- 사례의 수치·정답을 복사하지 말도록 안내하지만 일반 모델이 항상 지킨다는 보장은 없다.
- `Digest`는 prompt context hash를 캐시 식별에 쓴다.

`GenerationGuidanceStore`:

- `generation-guidance.json`, 해야 할 것/하지 말아야 할 것 각 최대 3,000자.
- 기본 프롬프트 전체를 자유 수정하는 기능과 다르다. 기본 프롬프트는 `GenerationPromptView`에서 실제 생성기의 system prompt를 읽기 전용 조회한다.
- 관리자 지침 + 승인 RAG를 생성에 전달한다.
- 이전 v1 코드 템플릿은 조회한 지침을 실제 적용하지 않아 교사 요구가 누락됐다. 최신 v3는 좁은 코드 기능에 맞는 profile 판독만 적용하므로 범용 지침 추종의 완성이라고 할 수 없다.

**여기서 “학습”은 프롬프트/RAG 적용이다. Gemma/DeepSeek 가중치 fine-tuning, 지속 학습, LoRA 학습 데이터 자동 검증 파이프라인을 구축한 것이 아니다.** 임베딩 검색·교사별 분리·버전 회귀 평가·적용 추적·승인 충돌 해결 등도 추가 검토가 필요하다.

## 15. 사용량/재시도/시간 제한

- `DeepSeekUsageHandler`는 HTTP 응답 usage를 기록하고 scope별 호출 budget을 공유한다.
- 일반 `/api/generate` scope 및 background generation budget은 코드 현재 18회다. 다른 middleware scope는 6회.
- 이는 **토큰 총량의 강제 상한이나 금액 상한**과 같지 않다. 18회 × 큰 prompt/완료 토큰이면 여전히 비용이 클 수 있다.
- 일반 생성 HTTP client timeout 480초.
- import deadline 210초, import gate 대기 15초.
- source와 completed import retention 2시간.
- GenerationResultCache retention 2시간, 한 snapshot 64MB, 전체 256MB, 시작 복구 최대 30건.
- stage series 작업 timeout은 `480 × 출력수`초, 단일 720초 코드가 있다. 브라우저 polling timeout과 따로 움직여 “조회 시간 초과인데 서버는 진행 중”이 될 수 있다.
- 형식 복구/출력 잘림/보완/재검토는 각 코드별 제한이다. 전체 호출 경로를 합쳐 확인해야 한다.
- 실패 재조회와 새로운 생성 POST를 구분해야 한다. 복구를 명목으로 매번 유료 새 요청을 보내면 안 된다.

## 16. 남은 문제/우선순위 — 해결했다고 말하면 안 되는 것

1. **범용 생성과 교사 로직 보존:** 최신 성공은 특정 3 STEP 몰질량 유형이다. 새로운 문제의 풀이 단계/통합 변형/피드백을 일반화하지 못했다.
2. **임의의 피드백 적용:** v3는 지원 profile 분류기다. 새로운 교사 요구를 코드가 자동 설계하거나 배워 수식에 적용하지 않는다. unsupported 오류가 나올 수 있다.
3. **원본 필기 OCR:** 파란 B가 본문 조건에 남는다. 문제 인쇄 내용과 풀이 주석 분리가 아직 미완료다.
4. **일반 AI 검토 오판:** 코드로 반증한 설명을 잘못 심사하는 사례가 있다. 좁은 경로만 제거했으며 일반 검토기의 독립성/정확성은 보장하지 않는다.
5. **PNG 최종 대조:** 현재 성공 JSON도 render unknown/review_required일 수 있다. 전체 PNG 대기 오류를 완전히 없앤 것이 아니다.
6. **독립 계산기 미지원:** 과거 신경/다른 과목에서 생성 차단이 발생했다. 현재 `GenerationQualityPolicy.CanStartFromSource`는 `sourceCheck?.State != "fail"`이므로 null/unknown만으로 시작을 무조건 차단하는 정책은 아니다. 완료는 report가 fail이 아니고 conditions/semantic-math pass가 필요하다. 이 정책이 미지원 유형의 실제 판독·AI 검토·생성 실패까지 해결했는지는 재검증하지 않았다. 과거 오류 문구가 곧 현재 정책이라고 단정하지 말 것.
7. **통합 변형의 교육적 다양성:** 잔류 종/미지수 위치/이전 비율 연결은 개선이지만, 전 유형에서 교사가 기대하는 새 고난도 아이디어 통합을 확인하지 않았다.
8. **비용:** 직전에도 실패 실험이 많은 토큰을 썼다. 단일 마지막 scope 951토큰을 전체 비용으로 표현하지 말 것.
9. **Gemma:** 최근 실제 동일 pipeline 품질/연결/속도 시험을 끝낸 것은 아니다. DeepSeek 템플릿 성공과 구분한다.
10. **결과/학습 UI:** 내부 3문항 파일 수와 사용자 1세트 수를 구분하고, 예전 테스트 기록/수동 GPT 자료가 사용자 목록에 섞이는지 재점검 필요.
11. **PDF:** 새 검증 PDF는 로컬 출력. 운영 학습 세트에 같은 파일을 정식 저장하여 다운로드까지 끝낸 검증과는 다르다. 과거 PDF 자동 교체는 안 했다.

## 19. 작업 환경/운영에서 겪은 실수 및 주의

- Linux 실행 중 DLL 덮어쓰기는 위험하다. 조용한 작업 시간 및 완료되지 않은 호출이 없는지 확인하고 백업 후 정식 stop/start 한다. 사용자에게 재시작을 숨기지 말 것.
- 직전 API deploy는 원본/학습/보고서 데이터를 지우지 않았다. 최신 사용자 요청은 프로그램 중단/문서 인수인계이므로 지금 추가 배포를 하지 말 것.
- SSH 문자열을 PowerShell에 잘못 이스케이프해 Python `-c`가 실패한 적이 있다. 이후 파일 기반 스크립트 전송 방식으로 바꿨다.
- private 이미지 fixture를 공개 주소로 POST하거나 서버에 새로 업로드하는 작업이 자동 승인 검토에서 거절된 이력이 있다. 서버에 이미 존재하는 원본을 서버 내부 loopback으로 처리하는 허용된 방식으로 검증했다. 다른 브라우저/클라이언트를 이용해 거절을 우회한 것으로 해석하면 안 된다.
- 개인 데이터/API키/접속 토큰이 로그에 있을 수 있으므로 증거 파일 내용을 그대로 공개하거나 MD에 전부 dump하지 않는다. 이 문서는 값 대신 경로/상태/결과를 기록한다.
- 브라우저 검증에는 Codex의 CUA API만 사용했다. browser state를 임의 fetch/storage/function injection으로 조작하지 않았다. DOM은 읽기 전용으로 확보했다.
- 사용자 소유 in-app browser tab을 report 읽기에 쓰고 마지막에 원래 `/learning/?problem=371409266cc44e23a7a3192b0155008a&tab=guidance`로 돌려놨다.
- 보고서 slot HTML 한 번에 출력된 문자열에는 `[Truncated]`가 들어갈 수 있었다. 긴 로그를 보고 임의로 다시 구성하지 말고 완전한 파일인지 검사한다.
- 최초 Markdown 감사는 읽기 검토였고 원본 PDF는 수정하지 않았다. 마지막 검증 PDF는 별도 새 결과다.
- 메모리 파일은 수정하지 않았다. 이번 인수인계도 사용자 저장소 안 문서이며 Codex 장기 memory 갱신이 아니다.

## 20. 이 문서를 받은 후 완료 판단 기준

기존에 “수정됐다”라고 말했던 것이 실제로 적용되지 않은 일이 반복되었다. 다음을 구분해서 보고해야 한다.

1. 코드만 바꿈.
2. 자동 테스트 통과.
3. 실제 모델에 같은 원본 문제/해설을 넣어 성공.
4. 풀이 로직·단계 사용·조건·보기·정답을 독립 대조.
5. 실제 최종 PNG/PDF/다운로드 화면까지 확인.
6. 현재 서버에 배포되어 사용자가 같은 흐름으로 이용 가능.
7. 어떤 문제 유형/모델/지침에는 아직 안 되는지.

현재 최신 상태는 특정 몰질량 유형에서 위 2~4와 로컬 제품 PDF 검토, 운영 코드/정적 반영을 확인한 것이다. **모든 피드백·모든 유형·PNG 검토·학습 PDF 다운로드·Windows 앱까지 전부 완료한 상태가 아니다.**

이하 자동 수집 부록에는 현재 Git 상태, 전체 미추적 파일, 소스/스크립트/문서/증거 경로, API 선언 위치와 주요 결과 요약을 넣는다. 실제 소스/바이너리는 저장소에 이미 있으므로 MD에 비밀 키나 수백 MB의 image/base64/DLL을 복제하지 않는다.
